# Digest — interop and deployment shape (round 2, assistant 1)

Lane: interop & deployment shape. Budget used: ~10 sources / ~18 calls. Accessed 2026-10-23.

## Findings

1. **OpenCode v2 merges every ancestor `AGENTS.md`; it is not nearest-only.** — source: https://opencode.ai/v2/docs/instructions/ | publisher: OpenCode (Anomaly) | published: unknown | accessed: 2026-10-23 | confidence: high | class: compatibility
   - Loads the global `~/.config/opencode/AGENTS.md` first, then every `AGENTS.md` from the current workspace directory upward. Documented example order: global → `packages/web/AGENTS.md` → `packages/AGENTS.md` → root `AGENTS.md`. "OpenCode combines the files and does not resolve conflicts between them." The source confirms `[global, ...project, ...configured]` and the discovery comment says "global then nearest-to-farthest project files" (https://raw.githubusercontent.com/anomalyco/opencode/dev/packages/core/src/config/plugin/instruction.ts, https://raw.githubusercontent.com/anomalyco/opencode/dev/packages/core/src/instruction-discovery.ts).
   - Deployment gotcha: the upward walk stops at the **home directory** when the workspace is under home, and only falls back to the project root when outside home. A repository under the home directory can therefore also load an unrelated `AGENTS.md` from an ancestor directory. `OPENCODE_DISABLE_PROJECT_CONFIG=1` skips project discovery but keeps the global file.

2. **OpenCode v2 recognizes `AGENTS.md` only; v1 still falls back to `CLAUDE.md`.** — source: https://opencode.ai/v2/docs/instructions/ and https://opencode.ai/docs/rules/ | publisher: OpenCode (Anomaly) | published: 2026-10-22 (v1 page) / unknown (v2) | accessed: 2026-10-23 | confidence: high | class: compatibility
   - V2 docs: "OpenCode V2 recognizes AGENTS.md only. It does not use CLAUDE.md as a fallback." V1 docs still document `CLAUDE.md` as a project fallback and `~/.claude/CLAUDE.md` as a global fallback, with `OPENCODE_DISABLE_CLAUDE_CODE*` switches.

3. **Nested `AGENTS.md` below the workspace are loaded lazily, nearest-first, with dedup.** — source: https://opencode.ai/v2/docs/instructions/ | publisher: OpenCode (Anomaly) | published: unknown | accessed: 2026-10-23 | confidence: high | class: compatibility
   - "Instruction files below the workspace are discovered as the agent explores the project. Reading a file or listing a directory loads any AGENTS.md files between that target and the workspace." Nested files load nearest-first and are deduplicated while their instruction entry remains in model-visible history. Edits to an already-loaded nested file are **not** auto-detected; start a new session. Root/ancestor files are watched and update mid-session.

4. **`instructions` entries load after `AGENTS.md` and are combined across config documents.** — source: https://opencode.ai/v2/docs/instructions/ and https://opencode.ai/docs/config/ | publisher: OpenCode (Anomaly) | published: 2026-10-22 | accessed: 2026-10-23 | confidence: high | class: compatibility
   - Relative paths/globs are searched in each directory from the workspace up to the project root; `~/` resolves from home; absolute paths are used as written; HTTP(S) URLs are fetched when config loads with a 5-second timeout. Missing files are skipped; a failed URL keeps its last fetched content (in memory). Configured instructions follow `AGENTS.md` in the order listed.

5. **No size cap or truncation is documented for OpenCode instructions.** — source: https://opencode.ai/docs/rules/ and https://opencode.ai/v2/docs/instructions/ | publisher: OpenCode (Anomaly) | published: 2026-10-22 | accessed: 2026-10-23 | confidence: medium | class: compatibility
   - Neither current doc states a byte/token limit, truncation, or per-file cap. Remote fetches have only the 5-second timeout; there is no documented persistent disk cache (source keeps a per-run in-memory `Map`). Absence of documentation, not an empirical test.

6. **Claude Code now reads `AGENTS.md` natively (v2.1.277+), but only when no `CLAUDE.md` exists in cwd or above.** — source: https://docs.claude.com/en/docs/claude-code/memory | publisher: Anthropic | published: unknown | accessed: 2026-10-23 | confidence: high | class: compatibility
   - Files that suppress `AGENTS.md`: `CLAUDE.md`, `.claude/CLAUDE.md`, or `CLAUDE.local.md` in the working directory or any ancestor. Files that do **not** suppress it: `~/.claude/CLAUDE.md`, managed `CLAUDE.md`, `.claude/rules/`. With support active, Claude reads every `AGENTS.md` and `.claude/AGENTS.md` in cwd and ancestors at session start, plus a subdirectory's `AGENTS.md` when it opens a file there with Read and that subdirectory has none of the three `CLAUDE.md` files.
   - The `Project instructions` setting can force both: `claude-md-or-agents-md` (default), `claude-md-and-agents-md`, `claude-md`, `managed-only`. Configured under `pluginConfigs` → `cc-plugin-agents-md@builtin` in `~/.claude/settings.json` or a `--settings` file; ignored in project/local settings.

7. **A root `CLAUDE.md` containing `@AGENTS.md` remains valid and is explicitly documented, but is no longer required on current Claude Code.** — source: https://docs.claude.com/en/docs/claude-code/memory | publisher: Anthropic | published: unknown | accessed: 2026-10-23 | confidence: high | class: compatibility
   - Documented as the bridge "when Claude isn't reading your AGENTS.md directly" — projects that also have a `CLAUDE.md`, sessions pinned to `claude-md`, or versions before v2.1.277. Caveats: imports resolve relative to the importing file, recursively expand to a **maximum depth of four hops**, skipping code spans/fenced blocks; a quoted path is not imported. "Keeping the import never makes Claude read AGENTS.md twice, whichever Project instructions value you use." Older guidance to use a SessionStart hook should be removed — it double-injects.

8. **Gemini CLI accepts `context.fileName` as a string or array and concatenates the hierarchical memory it finds; dedup is not documented.** — source: https://raw.githubusercontent.com/google-gemini/gemini-cli/main/docs/reference/configuration.md and https://raw.githubusercontent.com/google-gemini/gemini-cli/main/docs/cli/gemini-md.md | publisher: Google (gemini-cli) | published: unknown | accessed: 2026-10-23 | confidence: medium | class: compatibility
   - Syntax: `{ "context": { "fileName": ["AGENTS.md", "CONTEXT.md", "GEMINI.md"] } }`. The memory system "loads various context files from several locations, concatenates the contents of all found files, and sends them to the model with every prompt." Default filename is `GEMINI.md`; `context.memoryBoundaryMarkers` defaults to `[".git"]` and stops upward traversal. `context.discoveryMaxDirs` defaults to 200. Neither doc states whether identical content from two configured names is deduplicated; listing both names risks duplication. Unresolved.

9. **GitHub Copilot reads `AGENTS.md` natively and uses the nearest file, not a merge of all ancestors.** — source: https://docs.github.com/en/copilot/how-tos/configure-custom-instructions/add-repository-instructions | publisher: GitHub | published: unknown | accessed: 2026-10-23 | confidence: high | class: compatibility
   - "You can create one or more AGENTS.md files, stored anywhere within the repository. When Copilot is working, the nearest AGENTS.md file in the directory tree will take precedence." The same page says a single root `CLAUDE.md` or `GEMINI.md` is an alternative. Repository-wide `.github/copilot-instructions.md` and path-scoped `.github/instructions/**/NAME.instructions.md` are separate mechanisms; path-specific and repository-wide instructions are both used when both match.

10. **The AGENTS.md format itself recommends nested files only for large monorepos, with "closest file wins" on conflict.** — source: https://agents.md/ | publisher: AGENTS.md / Agentic AI Foundation | published: unknown | accessed: 2026-10-23 | confidence: high | class: practice
    - "Large monorepo? Use nested AGENTS.md files for subprojects… the closest one takes precedence." FAQ: "The closest AGENTS.md to the edited file wins; explicit user chat prompts override everything." This conflict model is the opposite of OpenCode v2's "combines and does not resolve conflicts."

## Answers to the six questions

- **Q1:** **Merged, not nearest-only, in OpenCode v2.** All ancestor `AGENTS.md` from cwd upward are loaded at startup, plus the global file, combined in order global → nearest → farthest; conflicts are not resolved (findings 1, 10). Subdirectory `AGENTS.md` **below** cwd are read lazily when the agent reads/lists in that subtree; nearest-first and deduplicated (finding 3). The `instructions` config is additive and loaded **after** all `AGENTS.md`, in listed order (finding 4). V1 differs: it still falls back to `CLAUDE.md`/`~/.claude/CLAUDE.md`, while v2 explicitly does not (finding 2). V1 docs say "all instruction files are combined" but also "the first matching file wins in each category"; read "category" as local vs global vs Claude fallback, not per-directory. V1's lazy-nested behavior is not documented.
- **Q2:** `@file` references are **not parsed automatically** in OpenCode v1; v2 docs likewise direct you to the `instructions` array rather than `@` expansion. `instructions` supports relative paths/globs resolved upward from the workspace to the project root, `~/`, absolute paths, and HTTP(S) URLs. URLs are fetched at config load with a 5-second timeout; failures keep the last fetched copy in memory; no persistent cache is documented. Globs re-evaluate on config change; local files update on change. No size cap or truncation documented (findings 4, 5).
- **Q3:** Yes — `CLAUDE.md` containing `@AGENTS.md` is still a documented bridge, but since Claude Code **v2.1.277** the native path is preferred: Claude reads `AGENTS.md` only when no `CLAUDE.md`/`.claude/CLAUDE.md`/`CLAUDE.local.md` exists in cwd or above (finding 6). Caveats: `CLAUDE.local.md` silently suppresses `AGENTS.md`; imports max out at four hops and resolve relative to the importing file; a quoted `"@AGENTS.md"` is not imported; and the import does **not** double-load when both files are active (finding 7). Where symlinks need elevated privileges, prefer the import over a symlink.
- **Q4:** `context.fileName` takes a string or array; e.g. `{"context":{"fileName":["AGENTS.md","GEMINI.md"]}}` (finding 8). The memory loader concatenates everything it finds across global, workspace/ancestor, and JIT locations. There is **no documented dedup**, so listing both names when both files exist is likely to duplicate content. For a single shared file, either set `fileName` to `["AGENTS.md"]`, or keep default `GEMINI.md` as a one-line `@AGENTS.md` import (Gemini supports `@file.md` imports relative to the importing file).
- **Q5:** For a 4-module Gradle repo under ~500 lines, **one root `AGENTS.md` with path-qualified sections is the better default**. Evidence: the format's own guidance reserves nested files for "large monorepos" (finding 10); OpenCode loads subdirectory files lazily and won't refresh edits mid-session (finding 3); Claude only loads a subdirectory `AGENTS.md` when it Reads a file there (finding 6); and Copilot uses the **nearest** file, so a module-level `AGENTS.md` would shadow the root file rather than add to it (finding 9). Nested files therefore produce different instruction sets per tool. Use nested files only where a module's rules are large enough to justify on-demand loading, and accept that Copilot will then lose root-level rules in that directory.
- **Q6:** Vendor-documented drift control is "one shared file, thin per-tool bridge": Claude documents exactly this pattern (`CLAUDE.md` with `@AGENTS.md`, plus Claude-specific lines below the import) and guarantees no double-load (finding 7). Gemini supports the same via `@AGENTS.md` imports (finding 8). Copilot needs **no bridge** for agent mode because it reads root `AGENTS.md` natively; it does not document `@`-import expansion, so a one-line pointer would not reliably deliver content (finding 9). Generator + CI check that bridges contain only the import line is reasonable practice, but no vendor documents a generator; don't present it as vendor guidance.

## Contradictions

- **Round-1 ambiguity resolved, with a v1/v2 split.** "First matching file wins" in the v1 docs is about categories (local vs global vs Claude), not about choosing one ancestor file. V2 docs and source explicitly merge all ancestor `AGENTS.md` (findings 1, 2). V1's exact per-ancestor merge behavior was not confirmed in v1 source.
- **Conflict model is not portable.** AGENTS.md standard says "closest wins" (finding 10); OpenCode v2 says it combines and does not resolve conflicts (finding 1); Claude loads each directory's `CLAUDE.md` first and its `AGENTS.md` after in `claude-md-and-agents-md` mode (finding 6); Copilot uses only the nearest `AGENTS.md` (finding 9). A nested-file layout behaves differently across all four.
- **Claude bridge status changed.** "Claude reads AGENTS.md only when no CLAUDE.md exists" is still true, but the bridge is now optional on v2.1.277+ rather than the only path; keeping the import does not double-load (findings 6, 7).
- **Gemini "list of names" vs dedup.** The config reference permits an array while the memory doc promises concatenation of all found files; neither states whether the same file discovered under two configured names is deduplicated (finding 8).

## Gaps

- Gemini's `memoryDiscovery` implementation was not inspected, so "listing both names duplicates" is inference from docs, not verified behavior.
- OpenCode v1 source was not read; v1 merge semantics are inferred from v1 docs phrasing plus v2 source. Test with two ancestor `AGENTS.md` files if still on v1.
- OpenCode's home-directory stop means a repository under the home directory may inherit an unrelated ancestor `AGENTS.md`; not empirically tested in this repository.
- No empirical size/truncation test for OpenCode; only absence of documented limits. Codex's 32 KiB cap was not re-verified.
- Copilot surface differences (chat/completions vs coding agent vs VS Code agent mode) were not fully verified.
- Exact publication dates for the v2 OpenCode, Claude Code, Gemini, GitHub Copilot docs and agents.md were not exposed; all accessed 2026-10-23.
