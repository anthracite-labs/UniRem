# Adversarial review — UniRem architecture spine

- **Gate:** architecture spine reviewer (adversarial lens)
- **Artifact under review:** `ARCHITECTURE-SPINE.md` (draft, 2026-10-23)
- **Evidence read:** spine in full; SPEC `spec-samsung-remote.md` (CAP-1..CAP-8); `protocol-reference.md`; `verification-matrix.md`; `EXPERIENCE.md` (final) in full; `.memlog.md`
- **Method:** for each seam, construct two units one level down (two independently built features, or two builders of the same feature) and check that **each unit obeys every AD to the letter** under its own reading. A hole is real only if both units survive an AD-by-AD compliance claim and still cannot interoperate or produce contradictory user-visible state.
- **Scope discipline:** no new features proposed. Every fix is a rule tightening, a missing ownership rule, or an explicit AD-1 carve-out. The spine was not edited.

## Verdict: pass-with-fixes

The paradigm, module graph, trust boundary, and capability ladder hold under adversarial reading; nothing here requires re-architecture. But the spine is **not yet safe to split into parallel workstreams**: H1–H5 are build-blocking divergence holes (H1 and H2 are rule-level conflicts, not just missing detail), and H6 is build-blocking for the receiver/phone split even though the spine defers its schema.

## H1 — critical — The one private-address gate cannot be shared, and AD-8 blocks the wake packet it must allow

- **AD:** AD-8, against AD-1; also binds CAP-5, CAP-6, CAP-1.
- **Contradiction in AD-8 itself:** AD-8 says "exactly one OkHttp interceptor rejects any host that is not RFC1918 or link-local before the request leaves… No custom socket factory or raw socket may bypass the check." CAP-5 requires the magic packet, and `protocol-reference.md` fixes it as "102 bytes (FF ×6 + MAC ×16) over UDP to ports 9 and 7, sent to the subnet-directed broadcast plus `255.255.255.255`." A limited broadcast is not RFC1918 and not link-local. Read literally, AD-8 forbids the packet CAP-5 mandates; read charitably, "raw socket may not bypass" makes the mandated packet a procedurally illegal act.
- **Unit A — `:tv` (pairing/channel/wake), builder "A":** implements `internal object PrivateHostInterceptor : Interceptor` with predicate `host.startsWith("10.") || host.startsWith("192.168.") || host.startsWith("fe80:")`, used on the remote-channel OkHttp client. Sends WOL from `:tv/wake` via a raw `DatagramSocket`. **Compliance:** AD-8's interceptor exists and is singular *in this module*; the WOL broadcast is the "exception named in the config comment and in this AD"; AD-1 is satisfied because the object is `internal`.
- **Unit B — `:cast` (renderer/server), builder "B":** implements `internal val isPrivate: (InetAddress) -> Boolean = { it.isSiteLocalAddress || it.isLoopbackAddress || it.isLinkLocalAddress }` (includes 172.16/12 and loopback; excludes IPv6 ULA), applied to the jUPnP HTTP client, to SSDP result filtering, and to the media server's peer check before serving a `Range`. **Compliance:** AD-8 says jUPnP gets "the same predicate" — B has one and only one predicate, and every `:cast` egress passes it; AD-1 is satisfied because it is `internal`.
- **Why both pass review:** AD-1's closed list ("The only cross-module declarations are `TvControl`, `RendererGateway`, `CapabilityResolver`, `CastSession`, and their input/output types; every other declaration is `internal`") gives a shared predicate **no legal home**. Two `internal` predicates is the AD-1-compliant answer, and AD-8's "same predicate" has no mechanism to become true across modules. The two units each wrote "the same predicate" in their own design docs.
- **Concrete break:** A home LAN addressed `172.20.x.x/24` (common on ISP routers). Unit A's interceptor rejects `GET /api/v2/` and the WSS upgrade: CAP-1/CAP-8 dead on that LAN. Unit B serves the cast fine because `isSiteLocalAddress()` covers 172.16/12. The verification matrix records a pass for that network type; the capability label says `Works`. Two AD-compliant units, one half-dead product, and the failure looks like a TV fault — precisely what AD-8's stated intent forbids. Second facet: the media server "binds to the session's private address" (AD-9) — A binds `0.0.0.0` and checks peers; B binds `first up site-local interface` — two interface-selection policies for one session.
- **Tightening rule (new AD-8 clause + AD-1 carve-out):**
  > **AD-8 (amended):** `:core` owns one `PrivatePeer` predicate, a total function over candidate destinations returning `Allowed`/`Denied`: allowed = RFC1918 (10/8, 172.16/12, 192.168/16), IPv4/IPv6 link-local, plus an enumerated destination list for the wake packet (the TV's subnet-directed broadcast and `255.255.255.255`, UDP ports 9 and 7 only). The OkHttp interceptor, the jUPnP transport configuration, both discovery filters, the media server's inbound peer check, and the WOL sender call this one implementation; no second predicate exists in any module, and no send path bypasses it. The wake destinations are an allowlist inside the predicate, never a bypass outside it.
  > **AD-1 (carve-out):** add `PrivatePeer` to the permitted cross-module declarations.
- **Note:** the media server's bind address selection belongs to the same rule: bind the interface address through which the session's TV was reached; if the route changes, the session restarts serving on the new address or ends visibly.

## H2 — critical — "Session end" has two deciders and `CastSession` has no declared writer

- **AD:** AD-6 (owners, FGS as adapter only), AD-9 ("stops at session end"), AD-3 (three clocks, one writer per state object). The gap: no AD says who may write `CastSession` or who decides that a session has ended.
- **Unit A — `:app/session.CastSessionOwner`:** holds `CastSession` as its single writer. Ends it on user Stop and on force-stop detection at next launch. On a renderer `STOPPED` event it shows the banner "Cast stopped" with "Start again" but keeps `CastSession` alive so the Cast slot returns to the session (UX: "If a cast session is already active, the slot returns to that session"). **Compliance:** AD-6 (process-scoped owner outside navigation), AD-3 (its clock is the only writer), AD-9 (it is the "session" whose end the server should honor).
- **Unit B — `:cast` (server + renderer adapter, package `session/` per the structural seed):** AD-9 tells the server it "stops at session end," so B implements a local end condition: no successful `GET`/`HEAD`/`Range` for 5 minutes, or `SetAVTransportURI` replaced, or the renderer reports `STOPPED` → stop Ktor, release the port, de-register the renderer, emit `CastFailure.SessionEnded`. **Compliance:** AD-9 to the letter (bounded serving, stops at session end — by its own definition of end), AD-3 (its own clock, its own state), AD-6 (it is not the owner; it is a protocol adapter inside `:cast`, and the structural seed gives `:cast/session` the "CastSession state").
- **Why both pass review:** the spine never says whether `:cast`'s `session/CastSession` *is* the process-scoped session object (the seed puts the type in `:cast`) or a fact stream the `:app` owner consumes. "One writer per state object" (State convention) is satisfied by *each* unit's reading because the object's home is ambiguous.
- **Concrete break (both directions):**
  1. User pauses playback (renderer `PAUSED`, no HTTP fetches — normal DLNA behavior), locks the phone for six minutes. Unit B's server self-terminates. Unit A still shows the session chip "Casting to Living Room TV"; the Cast sheet returns to a session whose resuming `Seek`/`Play` 404s. UX mandates "a session never migrates" and no silent stop — the user sees a live session that is structurally dead.
  2. Reverse: wifi blip on the phone side. Unit A decides the TV disconnected and ends the session ("Cast stopped"); Unit B's server is still bound and serving a cached TV fetch, and the TV keeps playing. The app says stopped, the TV plays on.
  3. The FGS adapter is a third candidate ender (notification "Stop" action) if H8 is not fixed in the same edit.
- **Tightening rule (new clause in AD-6, referenced by AD-9):**
  > `CastSession` and `MirrorSession` have exactly one writer each: the `:app` process-scoped owner, exposing exactly one `end(reason)` path. `:cast` and the FGS publish facts only (`RendererFact`, `ServerFact`, `FetchFact`, `ServiceFact`) as read-only flows; no other component writes session state or ends a session. The media server holds an idle/ranged grace window at least as long as the owner's liveness window and never self-terminates while an unended session claims it; a renderer stop is a fact that the owner maps to end. Session-end reasons are a closed set (`UserStop`, `RendererError`, `TvDisconnected`, `ProcessDeath`, `OwnerCancelled`) and the end reason is what the "Cast stopped" copy uses.
- **Note:** "TV disconnect" in the UX cast rules must be resolvable without borrowing AD-3's *connection-health* clock: the cast owner decides from cast facts (renderer reachability + fetch failures), not from the remote-socket health the topbar dot owns.

## H3 — high — The 8001/8002 observation has two consumers and no owner; "power state" is a fourth clock nobody owns

- **AD:** AD-3 (three clocks), AD-2 (wake maps native results to the three visual states at the `:app` edge), CAP-5 ("reports success only when the TV answers on 8001/8002"). Missing: an owner for power/awake state and for the probe observation itself.
- **Unit A — `:tv/wake.WakeProbe`:** after sending the packet, runs a 60s loop that opens a plain TCP connection to 8001, then 8002, every 2s; first accept = wake success; each attempt opens and closes a socket. Exposes `StateFlow<WakeState>`; the Wake sheet maps it to Submitted/Unconfirmed/Observed at the `:app` edge. **Compliance:** CAP-5 exactly ("reports success only when the TV answers on 8001/8002"), AD-2's cast/wake exemption (no tracker instantiated), AD-3 (its own clock).
- **Unit B — `:tv/channel.ConnectionHealth`:** post-disconnect backoff supervisor with jitter; every failed reconnect attempt to 8002 counts as a health failure and feeds the topbar dot and the offline banner. A successful WSS reconnect flips health to connected and reopens the remote socket. **Compliance:** AD-3 to the letter (health is its own type and owner), AD-6 (socket is UI-scoped; the supervisor only drives it).
- **Why both pass review:** both units observe the *same* physical phenomenon — "the TV answers on 8001/8002" — from different owners, and AD-3 explicitly blesses separate owners with no shared state and read-only combination for display. Nothing says probe connections must be attributable, and nothing owns "awake/asleep".
- **Concrete break:** the TV boots. Unit A's plain-TCP probe on 8001 succeeds (HTTP up), so the Wake sheet reports wake success; 8002's TLS stack is not ready, so Unit B keeps failing and grows backoff. The user simultaneously sees "Waking. This can take up to a minute." → success in the sheet, and the offline banner "TV didn't answer — retry?" with keys disabled on the Remote behind it. Worse: Unit A's ephemeral connects surface as TV-side `clientConnect`/`clientDisconnect` events; whichever unit handles those may count Unit A's own probe as "a TV connected" and cancel its own backoff, or treat each probe as a churn event and lengthen it. Both units remain internally consistent and AD-compliant; the product is self-contradictory. And SPEC CAP-5's "asleep/offline state" has no owner at all: both `:app` builders can invent one from the same socket-close fact and disagree.
- **Tightening rule (new clause in AD-3, referenced by AD-2 and CAP-5 mapping):**
  > Add a fourth owned value: **TV power state** (`On`, `Asleep`, `Unknown`) owned by one component in `:tv` that also owns all 8001/8002 observations. Wake never opens its own sockets: it requests the probe and consumes that owner's evidence (`StateProbe`) with the wake timeout policy. Probe and thin connections are tagged and never counted by the connection-health supervisor or by event handlers. `:app` display precedence between the four clocks is fixed and one-directional: identity-changed > unauthorized/pairing-required > offline > reconnecting > asleep > awake; a lower-precedence state is never shown as a contradicting banner while a higher one holds.

## H4 — high — Two capability-label authorities: persisted observation label vs derived resolution

- **AD:** AD-4 ("no module caches a resolved label independently"; step order 1–5), AD-5 (unknown firmware → `Not tested`), Persistence convention ("Room owns TV records, capability observations, probe results, and chip dismissals"), and the ER seed (`CAPABILITY_OBSERVATION { capability, label }`). Missing: who may persist a resolved label and who owns the label every surface displays.
- **Unit A — `:app/data.CapabilityRepository` + TV details:** every discovery/probe writes `CapabilityObservation(capability, label = CapabilityResolver.resolve(matrixRows, probeResults, declaredSurfaces))` into Room; TV details reads the latest observation label and renders it as the durable label (UX: "The durable capability label in TV details is the source of truth"). **Compliance:** `:core` does the resolving (AD-4), `:app` supplies rows and probe results (AD-4, AD-5), Room owns capability observations (Persistence), the ER seed literally stores a `label`; AD-5's "no module caches a resolved label *independently*" is read as "independently of `:core`" — satisfied.
- **Unit B — `:app/ui.CapabilityPresenter` (Remote/one-time chip/wake-cast gates):** never reads stored labels; calls `CapabilityResolver.resolve(...)` on demand from the matrix asset plus latest probe rows; stores probe results only as inputs. **Compliance:** AD-4 ladder applied per read, including AD-5's unknown-firmware rule (`Not tested` for a firmware no row covers); Persistence is respected because it only writes probe results.
- **Why both pass review:** the spine has a display rule ("no module caches a resolved label independently") and, in the same document, a storage schema with a `label` column and no owner. Two entirely reasonable units.
- **Concrete break:** the TV updates its firmware string (common on standby reboot). Unit B resolves via AD-5 to `Not tested` (no row covers the new string) and shows a dashed/`Not tested` gate; Unit A keeps serving the last observation's `Works`. TV details says "Works", the Remote says "Not tested", the one-time chip never appears because the stored label was never recomputed, and the wake gate (a Unit-A reader) stays enabled on a `Not tested` model while the cast gate (a Unit-B reader) disables. One TV, two capability truths, and CAP-8's "nothing claims support a physical test has not observed" is violated by whichever surface the user trusts.
- **Tightening rule (amend AD-4 + AD-5 + Persistence):**
  > `:app` has exactly one capability display owner. All labels on all surfaces are derived from the same input tuple — matrix rows, declared-surface observations, probe results, current firmware string, matrix version — by the single `CapabilityResolver`; every surface reads one flow. Persisted capability observations store **inputs only** (declared-surface absence, probe results, firmware observed, network type, matrix version, observed-at). If a label snapshot is persisted for diagnostics or "last verified," it is keyed by the full input tuple, is never read for display decisions, and is invalidated by the same owner that writes probe results.
  > **AD-5 (added sentence):** every derived label carries the `matrixVersion` and firmware string it was derived from; a firmware string change invalidates any stored snapshot.

## H5 — high — "MAC or device ID" is two identities: the same TV becomes two records and two Keystore aliases

- **AD:** AD-7 ("Identity is keyed by stable device identity, never by IP"; "Room stores the TV record and the Keystore alias, never the token or pin"), IDs convention ("`TvId` is a stable hash of MAC or device ID, never IP"). Missing: extraction precedence, normalization, and when identity is resolved.
- **Unit A — `:tv/pairing.PairingClient`:** `TvId = sha256(wifiMac)` (lowercased, separators stripped) from `/api/v2/`; used for every pairing attempt, including manual IP entry. **Compliance:** IDs says MAC is legal; AD-7 says key by stable device identity, never IP — MAC is stable per device, IP is not used.
- **Unit B — `:tv/discovery.SsdpDiscovery`:** `TvId = sha256(deviceId)` from the SSDP/`/api/v2/` device identity; discovery cards, Room upserts, and probe-result joins use this value. **Compliance:** IDs says device ID is legal; AD-7 is satisfied — device ID is the more stable identity, and IP is never used.
- **Why both pass review:** "or" is in the IDs convention; AD-7 never names the extraction source. Both modules are inside `:tv`, which is the only reader of the Keystore alias (AD-7) — this is not even a cross-module leak by the letter.
- **Concrete break:** the user pairs the TV once by manual IP (Unit A path, no discovery record) and later finds it by scan (Unit B path). Two Room TV records, two Keystore aliases, two pins, split probe results and chip dismissals, the wake MAC recorded under one record, the matrix's per-model pass applied to both. "Forget TV" on the duplicate leaves a live trust record and the TV still lists the phone. Second facet: the same TV on Ethernet vs Wi-Fi reports different MACs; identity-keyed-by-MAC reads that as "identity changed" → the re-pair flow, or (with Unit B) as the same TV whose wake MAC no longer matches the network path the matrix row was verified on (hidden condition in the IDs/AD-7 pair). Third: manual IP pairing has no MAC at entry time; Unit A mints a TvId from whatever `/api/v2/` returns or (worse reading) defers, and Unit B's discovery card shows a different TvId for the same TV in the same session.
- **Tightening rule (amend AD-7 + IDs):**
  > `:tv` owns exactly one `StableIdentity` extractor with fixed precedence — reported device ID first, MAC second, byte-exact as the TV reports it, with one normalization rule applied identically everywhere — and `TvId` is the hash of exactly that. A durable TV record and Keystore alias are created only against a resolved identity; a manual-IP target with no resolvable identity is session-only and says so. Identity is immutable per TV record and is never derived from the current connectivity path: a NIC change is not an identity change. The wake MAC is a separate stored field with its own provenance, and the wake matrix lookup states the network type it was observed on.

## H6 — high — AD-10's "handshake" and "version negotiation" have no envelope, so the two codebases cannot even fail compatibly

- **AD:** AD-10 ("The mirroring surface appears only after the receiver contract handshake succeeds. The contract is versioned and carries receiver version, viewer authentication, and the signalling endpoint. The app and the receiver negotiate a version before any media flows."). Open Question defers the v1 schema to the receiver workstream — acceptable for the media schema, not for the handshake envelope and negotiation rules, because two units are being built in parallel against nothing.
- **Unit A — `:app/mirror` (phone side):** implements the receiver check as `HEAD /unirem/ping` on the TV's 8001 with header `X-UniRem-Receiver: 1`; 200 → show "Start mirroring". On start, it opens WebRTC and treats SDP exchange as the version negotiation. **Compliance:** AD-10's surface gate and "negotiate before media" both claimed; no media flows before the check.
- **Unit B — `tizen-receiver` (TV side):** per the Open Question, the receiver workstream defines the handshake as a WebSocket `hello` on its own port carrying `{contractMajor, viewerAuth, signalling}` and never answers HTTP on 8001; "negotiate a version" = client sends major, receiver accepts or closes with a reason code only it defines. **Compliance:** AD-10 to the letter (versioned contract with the three named fields, negotiation before media).
- **Why both pass review:** the spine pins *properties* of the contract (versioned; carries three things; negotiated before media) and explicitly refuses to pin the contract itself. Two compliant implementations that share no wire surface at all. The phone can satisfy AD-10 and never see the mirror surface; the receiver can satisfy AD-10 and never be discovered.
- **Concrete break:** "Check again" never succeeds on a receiver that is running (or a stale 200 half-handshake lets the surface appear and then media negotiation fails with no shared failure vocabulary, so the UX cannot tell "receiver too old" from "wrong Wi-Fi"). AD-10's own prevention goal — "two incompatible receiver protocol versions" — is not prevented by the AD as written.
- **Tightening rule (amend AD-10; schema may stay receiver-owned):**
  > The handshake is one operation, not two: there is no separate presence check, and the mirror surface appears only on handshake success. The spine names the handshake transport and endpoint class, an integer `contractMajor` exchanged in a fixed first message pair, the direction and lifetime of `viewerAuth`, and the failure taxonomy (absent / too-old / busy / auth-failed) with one fixed `:app` copy per case and no capture start on any of them. The contract schema lives as a versioned in-repo artifact like the matrix, and the app's receiver port plus `MirrorFailure` map its rejections.

## H7 — medium — Tracker lifetime and the submit boundary are unbound: two compliant ring behaviors and two compliant voice mappings

- **AD:** AD-2 ("one `CommandTracker` per TV session in `:tv`"; "`:app` calls `submit()` exactly once per user gesture"; tracker "ignores evidence for older generations"), AD-6 (remote socket UI-scoped), IDs ("gesture generation is a monotonic `Long` per session"). Missing: what "TV session" means for tracker lifetime, and what a "gesture" is outside the D-pad.
- **Unit A — `:app/session.RemoteSessionOwner` + tracker:** creates the tracker when the socket opens and cancels it when the socket closes (the remote socket is UI-scoped and closes on background); the ring resets to Idle on return. **Compliance:** AD-6, AD-2 (one tracker per socket session; no shared state).
- **Unit B — `:tv/command.CommandTracker`:** a process-scoped tracker per `TvId` — a "TV session" is the TV record's session (AD-6's own "follows the user, not the screen" spirit); it survives socket closures because the socket is just a transport. After reconnect, no newer generation exists, so evidence for the pre-background press is accepted and resolves to `Observed`. **Compliance:** AD-2 to the letter — the stale rule only ignores *older* evidence; the generation is still the newest.
- **Why both pass review:** "TV session" is never defined for the tracker, and the spine uses "session" for three different lifetimes (socket, TV record, cast/mirror).
- **Concrete break:** UX: "an in-flight key is not claimed as observed. The ring resets to idle unless a fresh press starts a new command." Unit A satisfies it; Unit B shows `Observed` on return for a key pressed before backgrounding — a green ring for a press the product promised not to claim. Second facet (same hole, different unit pair): voice. Unit A maps a recognized "volume up" to a single `submit(VOLUP)`; Unit B synthesizes `Press` + `Release` frames and calls `submit()` for each, i.e. **two** submits for one user gesture — each unit can cite AD-2's "exactly once per user gesture" under its own definition of gesture (command vs frame).
- **Tightening rule (amend AD-2):**
  > Tracker lifetime is exactly the socket session: created with the channel session, cancelled with it; on socket close or target change the open generation resolves to `Idle` (never `Unconfirmed`, never `Observed`), and no evidence resolves a generation across a socket-session boundary. A generation is bound to the socket instance it was submitted on. `submit()` is called exactly once per user-expressed command, on all surfaces — D-pad tap, function key, voice command release/lock-done, dictation Send, text Send, pointer click; repeat frames and any synthesized press/release never submit. Exactly one tracker exists per target TV; no other component instantiates one.

## H8 — medium — FGS is "an adapter only" but nothing forbids it from owning locks, stopping itself, or running invisibly

- **AD:** AD-6 ("One foreground service per user-started cast or mirror session, with the matching type, is a lifecycle adapter only"; "MediaProjection consent is requested by an Activity and handed to the owner; the owner never launches UI"), AD-9 ("The session holds only the wake and Wi-Fi locks needed to serve while the screen is off and releases them at session end"). Missing: lock ownership and notification-denied semantics.
- **Unit A — `:app/session.CastForegroundService` (self-contained adapter):** acquires its own `PARTIAL_WAKE_LOCK` + `WifiLock` in `onStartCommand`, handles the notification "Stop" action by stopping the media server itself and `stopSelf()`; starts regardless of `POST_NOTIFICATIONS` (legal on API 33+; the notification is simply not shown). **Compliance:** AD-6 (it is a lifecycle adapter; it did not write session state), AD-9 (the session's locks are held while the screen is off and released at its own end).
- **Unit B — `:app/session.CastSessionOwner` + thin FGS:** holds the locks from session start to `end()` (AD-9's "the session holds"), the FGS only signals liveness and forwards intents to the owner; on a denied `POST_NOTIFICATIONS` it treats the session as foreground-only and does not start the FGS at all (UX: "the session can run while the app is open; background control needs the notification"). **Compliance:** AD-6 (adapter only), AD-9 (owner-held locks, released at end), UX notification state.
- **Why both pass review:** "the session holds" does not name the FGS, the owner, or `:cast`; "adapter only" constrains state-writing but not resource acquisition; the notification-denied state in UX is a description with no spine rule behind it.
- **Concrete break:** double wake locks and two release orderings; the notification's Stop can stop serving while the owner still reports an active session (directly feeds H2); and with notifications denied, the two units ship two different products — one keeps casting in the background with no visible control surface, the other ends the session on background. Same spec, opposite behavior, both defensible reads. Sub-question also unpinned: can a cast and a mirror run concurrently? ("One foreground service per user-started cast or mirror session" allows it; the singular "session chip" implies one.) Two builders will differ.
- **Tightening rule (amend AD-6):**
  > Device and network locks are owned exclusively by the process-scoped session owner and are acquired and released only by `end()`; lifecycle adapters (FGS, notifications, Activity consent hand-off) never acquire locks, never end a session, and never stop serving — they signal and forward. Notification actions map to owner intents by name. Without `POST_NOTIFICATIONS`, a session runs only while the app is in the foreground and ends on background with the fixed copy; the FGS is only started for a session that is allowed to outlive the foreground. Concurrency is fixed once: cast and mirror may/may not run at the same time, and the session chip model follows that decision.

## H9 — medium — Item handoff and the unguessable ID have two authorities; the failure modes are different products

- **AD:** AD-9 ("an `http(s)` URL with an unguessable per-item ID that resolves to one selected item only", "No `content://` URI crosses the boundary"), IDs ("`MediaId` is 128-bit random, base64url"), Persistence (Room owns records; the app does not request broad storage access per UX). Missing: who mints the ID, who shapes the URL, who owns DIDL/metadata, and how the picked bytes stay readable for the session.
- **Unit A — `:app/ui` + `:cast` server:** `:app` mints `MediaId` (IDs requires it to exist in `:core/model`) and passes `CastRequest(mediaId, contentUri)`; the server streams through a passed `ContentResolver` and builds `http://<ip>:<port>/m/<id>`. **Compliance:** AD-9 (unguessable, single item, no `content://` reaches the TV), IDs (MediaId used), UX (Photo Picker, no broad storage).
- **Unit B — `:app/data` + `:cast` server:** `:app` copies the picked item to `cacheDir/cast/<random>` and passes a `File`; the server mints its own path ID and builds `http://<ip>:<port>/media/<name>`, using `MediaId` only in telemetry and DIDL is assembled from the file. **Compliance:** AD-9 to the letter (the TV gets an http URL with an unguessable ID resolving to one item, no `content://` crosses), IDs is satisfied because a MediaId exists — its use is not specified by any AD.
- **Why both pass review:** AD-9 licenses the server to own the URL/ID but never says it must; `MediaId`'s destination is unspecified; nothing pins the lifetime guarantee of the picked bytes or the DIDL/metadata author.
- **Concrete break:** with Unit A, a Photo Picker grant is not durable across process death; after a force-stop/restore the URL resolves to nothing — the session says "still available" and 404s, or the TV fetches a dead URL. With Unit B, a long video copied to cache hits the cache/storage limit and fails before play, and "Start again" semantics differ from A. The two units also disagree on whether the served URL path is the `MediaId` (anything keyed to `MediaId` — telemetry, DIDL, diagnostics — diverges).
- **Tightening rule (amend AD-9):**
  > `:cast` owns `MediaId` minting, the URL path shape, and the id→bytes mapping; `:app` hands one opaque `CastItem` handle and never a URL. The item's bytes are guaranteed readable for the session lifetime by one named mechanism (a durable, re-validated permission with a documented copy fallback and a stated size limit), and unreadability at start is a named `CastFailure`. Exactly one component assembles DIDL-Lite and `protocolInfo` from the same `CastItem`, and the served URL carries the same `MediaId` used in diagnostics.

## H10 — medium — The matrix key is "model + firmware + network type" with no comparison semantics or vocabulary

- **AD:** AD-5 ("versioned in-repo artifact keyed by model, firmware, and network type"; "An unknown firmware matches only a row that explicitly covers unknown firmware"), Time convention ("Firmware is the string the TV reports and is never normalized"), Persistence (matrix is a read-only asset). Missing: exact-match rules, the `NetworkType` value set, and who determines network type.
- **Unit A — `:app/data` asset loader:** `rows.filter { it.firmware == reportedFirmware }`, byte-exact; network type derived from the SSDP `LOCATION` interface (`wlan0` → Wi-Fi). **Compliance:** AD-5 and "never normalized" to the letter.
- **Unit B — debug harness + probe runner:** trims and case-folds the firmware before lookup (writer and reader in the same module, so consistent), and writes network type from `ConnectivityManager` transport flags (`ETHERNET`, `WIFI`). **Compliance:** AD-5 ("A debug harness may append observed-effect rows with the same schema" — same fields, same names), and it never writes a production row.
- **Why both pass review:** "never normalized" binds the reported string, not the comparator; the schema's field types and allowed values are unstated; nothing names the authority for network type.
- **Concrete break:** after a debug session, a row written as `T-KTM2AKUC-1406.6` matches Unit B's lookup but not Unit A's (reports with trailing whitespace differ byte-for-byte); Unit B's `ETHERNET` rows never match Unit A's `Ethernet` display value. The same TV resolves `Works` in Remote and `Not tested` in TV details, and the debug harness's whole purpose — readable, reproducible evidence — fails the moment the production reader touches it. Wake's per-network-type commitment rides the same key.
- **Tightening rule (amend AD-5):**
  > `:core` defines the key as byte-exact strings (model, firmware) plus a closed `NetworkType` enum; exactly one component determines `NetworkType` from the observed path; the unknown-firmware case is a row with a literal sentinel (`*unknown*`) and never a wildcard; every row carries its `matrixVersion` and a firmware-change check invalidates snapshots. Readers never normalize; writers of any kind (including the debug harness) write through the same schema and value set.

## H11 — medium — The LAN gate's result has no permitted cross-module type, so `:tv` and `:cast` invent separate denial paths

- **AD:** AD-11 ("one app-level `LanAccessGate` owns permission requests and diagnostics. `:tv` and `:cast` never request permissions and never launch UI"), against AD-1's closed declaration list.
- **Unit A — `:tv` (discovery/pairing):** never asks for anything; discovery simply yields nothing when the permission is absent, and pairing maps `SecurityException`/`IOException` into `TvFailure.NetworkDenied` with a generic offline banner. **Compliance:** AD-11 (no permission requests, no UI), the Errors convention (one sealed failure per module).
- **Unit B — `:cast` (renderer/server):** never asks; bind/connect failure maps into `CastFailure.BindDenied` and the sheet shows "Check again"; the media server silently doesn't bind. **Compliance:** AD-11, Errors convention.
- **Why both pass review:** the gate is an `:app` component; publishing its result to `:tv`/`:cast` would be a new cross-module declaration AD-1 forbids. Both modules therefore discover denial as an error after attempting — the only structurally legal option.
- **Concrete break:** UX's "Local network denied" state — "UniRem needs local network access to reach your TV" + "Open settings" / "Not now", with scan and manual IP visibly blocked — is unreachable from any surface: the user sees "TV didn't answer" and "Retry" loops that never mention the permission, and the manual-IP fallback (always offered) silently fails. Exactly the silent failure AD-11 exists to prevent.
- **Tightening rule (amend AD-11 + AD-1 carve-out):**
  > Add the read-only `LanAccess` state to the permitted cross-module declarations. `:tv` and `:cast` consult it before any attempt and map its denial to exactly one failure each (`TvFailure.LanDenied`, `CastFailure.LanDenied`); `:app` maps both to the single gate explainer. The gate owns all permission UI, the isolation diagnostic, and the manual-IP path — a denied gate blocks scan and manual IP identically.

## H12 — medium — `TvControl`'s operation vocabulary, the repeat engine, and pointer coordinate meaning are unpinned; two engines double-step the D-pad

- **AD:** AD-1 (cross-module declarations are "`TvControl` … and their input/output types" — plural but unshaped), AD-2 ("repeat frames send `Press`/`Release` without calling it"; UX fixes repeat at 500ms then 80ms), Visibility convention (":app never imports `KEY_*`"), CAP-4 (voice mapping lives in `:app`).
- **Unit A — `:app/ui` D-pad + `TvControl` as edge ops:** the D-pad owns repeat timing (UX's 500/80ms) and calls `TvControl.press(key)` / `TvControl.release(key)` through a shared `RemoteCommand` enum it also uses for voice mapping (CAP-4's "command mapping" in `:app`). **Compliance:** AD-2 (repeat frames don't call `submit()`), Visibility (`:app` never sees `KEY_*`; the enum is an input type), CAP-4.
- **Unit B — `:tv/command` as the repeat owner:** `TvControl` exposes `pressHold(key)` / `releaseHold(key)` and `:tv` runs its own coalescing repeat loop (protocol reference: "hold uses `Press`/`Release` or a repeat loop with coalescing"); `:app` sends one edge pair per hold. Pointer input is `movePointer(x, y)` where x/y are absolute TV coordinates. **Compliance:** AD-1 (input type), AD-2, protocol reference's either/or, and the Visibility convention (frame-level detail stays internal).
- **Why both pass review:** AD-2 says repeat frames exist but not who emits them; AD-1 permits input types but never shapes them; the protocol reference explicitly allows two repeat implementations. Pointer semantics ("Position":{"x":10,"y":-4"} — absolute vs delta) are equally unstated.
- **Concrete break:** with A's D-pad (which holds 80ms timing) against B's `:tv` loop, a hold produces two interleaved repeat streams — double-stepping and dropped releases; with voice, A's mapping targets `RemoteCommand` while B's implementation expects frames, so "volume up" is either unmappable or maps to a different code than the D-pad uses. With the pointer, a delta-producing touchpad against an absolute-expecting channel (or vice versa) moves the cursor to nonsense positions — and both units' own tests pass.
- **Tightening rule (amend AD-2 + name `TvControl`'s inputs in AD-1):**
  > `TvControl`'s operation set is fixed: discrete press/release edges in a typed command vocabulary owned by `:tv` (`RemoteCommand`), text with explicit IME lifecycle, pointer with a named coordinate space fixed by a test fixture against the protocol reference, and wake as a separate operation. Exactly one repeat engine exists — in `:tv`, driven by press/release edges from `:app`; `:app` owns the UX thresholds (500/80ms) as configuration, not as a frame sender. Voice, text, and pointer mapping tables target the same `RemoteCommand` type.

## Cross-cutting root cause

H1, H7 (partially), and H11 are one structural problem: **AD-1's closed declaration list predates AD-8/AD-11's need for shared runtime values** (`PrivatePeer` predicate, `LanAccess` state) and AD-2's need for a shared command vocabulary shape. The four named declarations are the *state owners and protocol seams*, but not the *shared values*. Every implementer resolving this alone will duplicate (H1's two predicates) or silence the cross-module condition into a module-local failure (H11). Fix the list once, deliberately.

## Holes probed and held (no fix required)

- Trust material: Room stores only the alias, `:tv` is the only reader; no AD-compliant leak found. The pin-before-token order survives both "before request" and "before first frame" readings.
- AD-4's evaluation order 1–5 is deterministic under every reading I tried; the preemption between "declared absent" and "probe pass" is resolved by the ordering itself.
- The cast/wake exemption from `CommandTracker` is unambiguous; H3 is about the probe observation, not about the exemption.
- `:core` purity, per-module sealed failures, time/Instant rules, RedactedLog targets: no dual-reading hole found.
- Chip dismissal keying (`tvId` + capability + firmware) matches UX's "never returns unless re-paired / firmware changes / probe result changes"; H4 and H10 cover the label/key side.

All fixes are rule tightenings and cross-module carve-outs; none changes the four-module graph, the paradigm, or any capability's commitment.
