## Select matrix (technical only)
| Dimension | A: phone-hosted stream → AVTransport URI | B: WebRTC to TV receiver | C: DIAL / Smart View app-to-app |
|---|---|---|---|
| Latency (expected, unverified) | High: capture+encode+HTTP/TCP+TV buffer, typically multi-second; TV expects bounded file | Low: sub-second capable (game-mode WebRTC design target); phone encode + LAN RTT dominate | N/A (control plane only; media latency = whatever transport you pair it with) |
| Interactivity | Video/slides OK; gaming/interactive NO | Video OK; interactive/gaming POSSIBLE (only low-latency option; needs 2022+ + tuning) | No media by itself |
| Battery/thermal (phone) | High sustained (encode + serve); unverified magnitude | High sustained (encode + WebRTC stack); unverified magnitude | Low (discovery/launch/messages only) |
| Build cost | Low spike (no TV app) but high risk of DMR rejection | High (signaling + LAN STUN/TURN + SDP imageattr + TV Web app + Seller Office path) | Medium (sender + installed Tizen receiver + custom channel) |
| Receiver dependency | None (stock DMR) — IF it accepted live URIs, which is unverified | Requires custom Tizen Web receiver (2022+ for game mode); plain browser-URL path unverified | Requires custom installed Tizen receiver |

**Spike order:** 1) B-WebRTC spike first (only path with documented low-latency live primitive + shipped game-streaming precedent; proves interactivity ceiling). 2) A-AVTransport falsification spike in parallel/2nd (cheap: serve HLS/live-TS from phone, try SetAVTransportURI on target models; expect failure — one test kills or revives it). 3) C-DIAL/SmartView launch harness last (needed regardless as the launch/control plane for B; does not solve media by itself).
**Reasons:** B answers the hard requirement (live + interactive); A is cheapest to disprove and unblocks a no-TV-app fallback if it surprisingly works; C is scaffolding, not a transport — build it to serve B, not instead of B.
